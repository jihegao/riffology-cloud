# Browser Preview orchestration

G2A freezes these authenticated Workspace routes. Reads never create builds or execute models.

- `GET /api/workspaces/:workspace/browser-preview?revisionId&profileId`: `{currentRevisionId,revisionId,build,stale,modelSpec,reasonCode,delivery}`. Optional identifiers are validated; omitted Revision selects the authoritative saved head. No saved head returns `preview-no-saved-revision`; unclassified durable discovery returns `preview-discovery-pending`, without inventing a profile. An old Revision remains read-only and its own build cannot update the new head.
- `GET /api/workspaces/:workspace/browser-preview/packages/:packageIdentity`: canonical UTF-8 envelope bytes, only through an authorized, durable server receipt. No client object keys or fallback to head.
- `POST /api/workspaces/:workspace/browser-preview/verify`: exactly `{revisionId,packageIdentity,parameters,seed,intent:'experiment',idempotencyKey}`; returns `{verificationId,experiment}`. The server loads the exact frozen saved source, checks the canonical platform adapter, and recomputes using existing SimulationHost. Browser results are not inputs or Evidence. POST preserves the existing server Experiment ready admission gate, rechecking authoritative Catalog scope/readiness across awaited source reads; accepted receipt GET remains available under maintenance authorization.
- `POST /api/workspaces/:workspace/browser-preview/retry`: exactly `{revisionId,profileId,buildIdentity,idempotencyKey}`. Only a server-resolved failed row accepts a bounded retry. Returns `{retryId,status:'accepted',revisionId,profileId,buildIdentity,...view}` after durable receipt. Repeating a key never resets attempts; a new explicit key may recover an exhausted build with the same references and create-only object identity.
- `GET /api/workspaces/:workspace/browser-preview/retry/:key`: `{retryId,status:'absent'|'accepted',captured:{revisionId,profileId,buildIdentity}|null}`; read-only acknowledgement-loss reconciliation.
- `GET /api/workspaces/:workspace/browser-preview/verify/:key`: `{verificationId,status:'absent'|'accepted',captured,experiment}`. Captured intent contains Revision/package/input identity without the idempotencyKey, which is represented by verificationId. Refresh does not mint a key or submit; absent recovery requires explicit retry of the original captured intent.

`delivery` contains `{executionOrigin,hostModule:{url,sha256,byteLength},rendererModule:{url,sha256,byteLength},assetBaseUrl,profile}`. Execution origin is a fixed platform configured independent HTTPS site. App assets are immutable digest/path whitelist bytes, with no credentials forwarded to the assets binding. Profile snapshots come only from verified platform registry and are retained with their immutable delivery identity; no client manifest is trusted. Unknown or unavailable historical runtime assets fail explicitly, never upgrade a package silently.

## Persistence and recovery

The saved checkpoint journal transaction writes a discovery record with the private exact Turn identity and receipt, the sixth logical build wake, and the merged physical alarm. This applies equally to completed, failed, cancelled and interrupted saved Turns. The journal operation remains synchronous with no external I/O; storage transaction operations are asynchronous. All legacy migrations and initial-base preservation checks remain enabled. `sync()` acknowledges durability; it does not repair a separately committed alarm gap.

Every alarm mutation preserves workspace, Turn, service, observer, simulation and browser build wakes. Maintenance finally blocks visit browser build even if an earlier domain throws. R2 packaging is separate, create-only, with durable source reference intent before PUT and digest/length readback before receipt. Retry attempts and per-delivery work are bounded. Model generation, Pi and release are not prerequisites for maintenance.

Historical source authority remains the saved journal row and its immutable RevisionStore manifest. RevisionStore orphan collection scans retained manifests and does not delete those references; browser package keys are outside the Turn orphan prefix. Build reference records supplement this inventory and must not be removed while a receipt is retained.

Library copies currently have a trusted initial-workspace archive but no saved Turn. Their browser build requires a separate initial-derived source identity and authorization contract in G3/G6; this phase does not fabricate a saved Revision. Existing server Run remains available.

## Composite asset preparation

All five Gateway configurations now serve ASSETS from `.local/browser-preview/gateway-assets`. Run `node scripts/m3/materialize-browser-preview-web.mjs` after preparing the verified fixed runtime assets. The script validates the committed execution index, builds a fresh web directory, verifies every immutable app asset, then replaces the previous generated directory and writes `gateway-assets-receipt.json` with every web file hash/length and app asset descriptor. Runtime bytes remain generated local files, not Git files. Read-only system preflight reports missing/drifted assets as blocked; local launch prepares them first. Production execution origin defaults empty and fails closed until a separately reviewed independent site is configured.

The formal ASSETS test uses the actual Gateway Worker, the combined directory, a real local HTTP listener and Chrome module imports. All 40 immutable app assets are checked against their recorded SHA-256/length; the trusted panel module and host/renderer imports pass. This delivery test is separate from the complete product research loop. Formal core tests now include capture sync uncertainty, concurrent same-key actual SimulationHost submissions, old-head Verify, ACL revocation during R2/source awaits, explicit retry receipts and exhausted retry/new key recovery, frozen profile retention, and a third-rearm crash snapshot with no fourth I/O. A complete Gateway/RevisionStore/native acceptance driver is independently owned by G3.

The async transaction primitive follows the [official SQLite storage API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/#transaction); `sync()` is only the durability acknowledgement.
