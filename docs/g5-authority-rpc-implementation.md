# G5-A private authority RPC

Status: implemented and tested locally on the integration base; no Worker or Durable Object was deployed by this change.

`G5ControlledWindow.operatorSnapshot()` is now the single private aggregate for the active frozen window. It starts from Guard-owned task, call, Turn, deadline and closed state, then resolves every persisted `runtime_identity` against the fixed G5 token namespace, production money actor and per-dispatch Tool Bridge actor. It reports task and dispatch counts, group intents, Simulation and Service Run counts, deadline origin, pending and unknown counts per domain, recorded/reserved money occupancy and the maximum occupied Turn. A missing binding, malformed settlement, identity mismatch, read timeout or money-reference conflict throws; the temporary operator Worker returns only `operator-unavailable` in that case.

`inspectTask` does not accept receipts from the caller. The Guard resolves the bound Turn task and its persisted runtime identity, asks the exact Workspace actor for the terminal saved Turn, current checkpoint/version and retained completed tool event IDs, and joins that proof to closed token, money and tool settlements plus each Guard-persisted authority-call context. The requested fixture ID must also match the Workspace's durable ordinary-user request key `${windowId}-${fixtureId}-turn`; it is not echoed as identity evidence. The current implementation intentionally fails closed if the inspected Turn is no longer the Workspace head or its completed tool events have left the retained event window. The serial driver inspects immediately after each Turn, before admitting the next one.

`inspectRun` first resolves the globally unique Guard task whose `bound_id` is the requested Run. It then selects the Workspace from a Guard-persisted Turn identity and requires the Workspace's private Simulation record to match the same G5 task key, tenant/user scope, Run ID and artifact hash and to be `completed`, released, and backed by a non-null platform release proof. The fixture ID must match the durable request-key prefix `${windowId}-${fixtureId}-run-` and a positive Run ordinal. A caller boolean or caller-only fixture label is never used.

`inspectFinal` compares the complete set of Guard-bound Simulation Run IDs with all G5 Simulation records found in the three authoritative Workspace actors. Each Run must be `completed`, released, and backed by a non-null platform release proof. It also compares Guard-bound `group` task IDs with actual Workspace group records, requires each Group itself to be `completed`, and requires every child to be one of those terminal released Runs. Project, Turn, Run, group-intent-task and total-task counts, plus the admission `closed` flag, come from durable Guard state. The caller's expected counts are bound into the final receipt but do not create or override observed counts; an open window is returned as `closed: false` for the hardened driver to reject.

`inspectAdmissionContract` accepts no payload. It derives the 63 normal tasks, 66 maximum tasks, three group-intent tasks and `guard-task` admission mode from the persisted Phase A policy and fixed task rules, then hashes that derived contract. A 63-task legacy policy or any other policy shape fails closed.

Group creation is now a first-class G5 task. `kind: "group"` consumes the global task limit while leaving `maxSimulationRuns` unchanged. `submitExperimentGroup` derives the parent from the Workspace's saved head and its private G5 Turn route, registers and claims the group task before local creation, then binds the durable group ID and obtains and confirms a one-shot start grant. If the Workspace commit succeeds but a Guard RPC acknowledgement is lost, an identical retry replays the local group and completes bind/start confirmation. If creation fails after the Guard claim and no local group exists, the claimed task remains a global hold; it is not refunded or bypassed.

The temporary operator Worker exposes only capability-protected POST actions `snapshot`, `inspectAdmissionContract`, `inspectTask`, `inspectFixtureTask`, `inspectFixtureTerminal`, `inspectRun`, `inspectFinal`, `snapshotReadonlyCounters`, `attestReadonlyInterval`, and `close`. Its only binding remains the global Guard actor; ledger and Workspace namespaces stay private to the production Worker. `createG5AuthorityAdapter` maps an in-Worker stub to the serial driver's authority interface. `createG5OperatorHttpAuthority` is the bounded Node-side client: it calls only `/operate`, refuses redirects, limits response bytes, keeps the capability request-only, and performs the snapshot-digest close handshake before returning a sanitized close receipt. The Worker must still be deleted after evidence collection.

Proposal B has an isolated `inspectFixtureTask` path. The per-dispatch Tool Bridge reads its closed, quiescent SQLite ledger and asks the exact Workspace actor for retained `tool.completed` events and the current saved Turn head. It accepts exactly six event-derived command IDs in bash/read/bash/bash/read/bash order, six unique effect and event IDs, the frozen failed and repaired `model/model.py` digests, a nonzero compile result containing `SyntaxError`, a final zero compile result, and a new saved Revision whose archive digest matches the Turn checkpoint. The returned proof contains only identities, exit classification and SHA-256 receipts; source content, stdout, stderr, command payloads and capabilities never cross the operator response.


Validation includes TypeScript typecheck and the focused G5 authority, driver, operator, export and Workerd suites. The Workerd tests exercise real Guard and Workspace Durable Objects with bounded R2 result and trace-audit objects, persisted receipts, pending rejection and restart replay. All proofs in these tests are local fixtures; production authority remains unverified until the exact release is deployed and read back.

## Two-stage fixture authority

The server owns the 18-entry Proposal B order in `services/model-budget/g5-fixture-manifest.ts`, pinned to final fixture bytes `673d0cbe930990602649aaa9d746e16ad29280981f5f7be336b368388ceee753`. It derives the six category relations, run cardinalities `[1,2,1,1,6,2]`, three group intents and 39 Runs. The caller supplies only fixture, Workspace, Turn, Run, Group and Claim identities plus the observed saved version.

`inspectFixtureTask` is the post-Turn phase. It reuses the Guard task, saved Workspace head, provider receipt and closed model/money/tool ledgers. Repair fixtures additionally read the private six-command Tool Ledger proof. The Guard writes a `turn-verified` row with the server manifest digest and the preceding terminal receipt hash in one SQLite transaction. The next fixture cannot enter this phase until every preceding row is terminal.

`inspectFixtureTerminal` is the post-Run/Group/Claim phase. Workspace durable state must show the exact run count, completed and released Runs with release proof, the saved version, a completed exact-child Group when required, and verified current evidence claims whose references point only at those Runs. For every Run the Workspace reads the bounded result envelope and canonical `trace-audit.json` from R2, verifies their digests and shape, and recomputes finite and nonnegative values, strict frame and time order, conservation, and `queue_length == waiting`. Conservation treats `active` as the total number currently present; `waiting` is its queued subset and is not added twice. The Guard independently binds every Run to its simulation task and fixture request key. Only a fully accepted result is persisted as the terminal chain receipt.

Before creating any Project, the live driver requires the authority's exact admission contract: 63 normal tasks, 66 maximum tasks, three `guard-task` group intents. It pins both fixture receipts to manifest `673d0cbe930990602649aaa9d746e16ad29280981f5f7be336b368388ceee753`. Stage two requires Run ordinals to cover `1..N` exactly, binds a Group to its started and confirmed Guard group task plus the parent Turn, and verifies Claim creator, `throughput` metric, kind and exact Run coverage (including the six baseline/intervention references for the group delta). Terminal responses bind the stage-one receipt digest and saved source. On normal completion the driver closes admission first, then accepts only the hardened final shape with `groupIntentTasks`, total `tasks`, and `closed: true`.

The frozen manifest separates machine facts from interpretation. `mean_wait` cannot be reconstructed from the canonical trace rows, so neither its paired ordering nor a zero value is marked verified; those checks are recorded as `unassessed` with the originating Turn. The result envelope digest binds its persisted numeric throughput, but the trace audit does not contain the time denominator needed to independently recompute that rate. Group Claim authority therefore proves the persisted numeric delta and exact six-artifact coverage without describing the rate as trace-derived. Natural-language explanations remain `unassessed` and never enter the verified machine assertion set.

Readonly proof is split into transport observation and durable authority. Browser GET evidence such as path, status, response bytes and body/header hashes remains `transport-observed`; Guard does not sign it as a server fact. `snapshotReadonlyCounters` stores the exact server-derived Workspace revision and complete Run/Group inventory inside the receipt digest. The Workspace independently enumerates all in-scope Runs, requires each bounded R2 artifact, terminal release and release proof, validates every Group and Claim, and derives the exact Run/Group/Claim/source-version inventory. A successful research export persists a sanitized durable receipt keyed by the actual ZIP body digest, with the exact exported revision, inventory, source versions, manifest digest, entry count, bytes and response metadata. `attestReadonlyInterval` accepts only a byte-identical binding rebuilt from those Workspace facts and the persisted export receipt, requires identical settled counters before and after, and stores the resulting Guard receipt.

Every reopen terminal must bind exactly one preceding `before-reopen-readonly` receipt and one current `research-export-readonly` receipt. The export inventory must equal the earlier inventory plus that fixture's two new Runs and two new Claims, with no Group change or reused identity. Final authority requires all three reopen terminals, six unique durable attestation receipts, and an exact union matching all 39 Runs, three Groups and 24 Claims. Missing, extra, reused, caller-only or unsettled evidence fails closed. The terminal and final receipt digests include the readonly receipt roots, while their public response shapes remain compatible with the hardened serial driver.
