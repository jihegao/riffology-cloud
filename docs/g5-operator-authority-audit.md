# G5 operator authority audit

The tracked temporary Worker in `services/g5-operator/index.ts` is the smallest current path to the production G5 Window Guard. Its Wrangler binding names the existing `G5ControlledWindow` class in `riffology-m1-gateway-staging`; `getByName("g5-controlled-global-v1")` therefore invokes the existing Durable Object through private RPC. The Worker exposes one capability-protected temporary endpoint because an external CLI cannot invoke a Durable Object RPC directly. It returns a sanitized Guard summary. Closing requires the exact preceding raw-snapshot digest, the existing window ID, an explicit confirmation value, and `x-g5-mutation: close-admission`; it then verifies a second snapshot. The Worker must be deleted after evidence collection. This commit does not deploy it.

This is sufficient for the `G5_WINDOW_GUARD` part of `readState` and for `closeAdmission`. It deliberately returns `authority: g5-window-guard-only` and `completeLedgers: false`. The token ledger requires a tenant plus full runtime identity, the money ledger exposes per-reference and per-Turn settlement rather than a global snapshot, and the tool ledger is a per-Workspace/Turn actor. A trustworthy aggregate therefore needs a new private `G5ControlledWindow.operatorSnapshot()` RPC that reads its stored runtime identities and authority call contexts, queries all three bound ledgers, and returns per-Turn receipts plus aggregate pending/unknown counts. Until that interface exists, the operator control must not map this Worker response directly to complete `readState` or open a next task based on it.

`readConfig` and `deployExact` must be backed by the Cloudflare Versions API or Wrangler version upload/deploy against the private compiled overlay. The trusted receipt must bind the uploaded version ID, source/config artifact SHA-256, deployment ID, and a subsequent active-version readback. A local copy of the config or a successful `wrangler deploy` exit code is not independent readback. Secret values are neither readable nor part of the receipt; required secret names and active binding types are checked separately. No repository API currently implements these two ports.

There are no backend methods named or equivalent to `inspectTask`, `inspectRun`, or `inspectFinal`. The ordinary product sources that can support a future implementation are Workspace snapshot and files/revision routes, simulation/service Run detail, RevisionStore/R2 artifacts, and the private G5/three-ledger receipts. These must be joined by exact project, Workspace, Session, Turn, task, Run, revision, artifact, runtime, and provider identities. The current `DurableOrdinaryRunner.createReconcile()` stops at `manual-evidence-checkpoint-required`; it is not an authority for the remaining seventeen tasks or thirty-nine Runs. Do not implement those inspectors as booleans supplied by the caller.
