# Queue: 受邀用户研究与发布协议

问题：**增加服务台，在不同到达率下会怎样改变等待时间？**

本文件是普通产品路径的作者、审核者和用户指南，不是已发布模型或
线上成功报告。首页仅在官方目录返回 `model_id=queue-research` 的已发布版本时
启用 Queue 入口；用户仍须明确选择版本、确认创建独立副本。

## 作者：先冻结假设，再请求建模

向普通建模助手提交下面的研究简述；不能直接写数据库或把仓库测试模型晋升为官方案例。

> 建立单队列、多服务台、先到先服务的排队模型。时间单位为分钟；到达间隔
> 和服务时间先采用独立指数分布，每台服务速率固定为每分钟 1 人，不考虑
> 放弃、优先级或服务台差异。研究到达率 0.6、0.9 和服务台数 1、2 的组合。
> 请先说明假设与指标，提供可运行预览，然后对每个组合使用 seed 7、8、9。
> 每次运行 1000 分钟，前 100 分钟作为预热；保留逐次运行数据，不把示例数字
> 当执行结果。保存原模型版本及基线，比较时不要覆盖历史结果。

这组设计共 12 次正式运行，不是执行授权。费用冻结未完成前不得发送这段建模请求
或启动正式实验；本地已有兼容预览的操作与正式实验单独记账。

指标在 Model Spec、实现、导出中保持同一口径：预热后到达并开始接受服务的顾客
等待时间均值、开始服务人数、预热后到达但到截止仍未开始服务的人数、时间加权
队长和服务台利用率。截止截尾比例必须显示；不能把未开始服务者当作零等待。
三个 seed 只提供初步随机重复，不支持笼统的显著性或现实因果结论。

## 普通产品路径

1. 作者保存模型；检查预览与保存版本一致，参数和 seed 生效。
2. 通过正式实验保存基线及比较，逐条核对参数、seed、版本和实际结果。
3. 从 Export 下载研究包，在独立目录按包内 README 重跑，比较数值与来源。
4. 作者提交 `queue-research`、版本 `1.0.0`，附假设、实验设计、指标口径与局限。
5. 非作者管理员审核冻结版本；修改要求退回作者生成新 Revision，管理员不改作者模型。
6. 新用户从官方目录选择版本创建副本，修改参数并运行；确认原官方版本及作者项目未变。

首例通过只完成 #35 的 Queue 子项。Inventory、Maintenance 不记为完成。

## 新用户任务卡

- 首次访问：打开 Queue 副本，观察运行，改一个参数并解释你预期会发生什么。
- 正式研究：选择一个比较问题，执行多个 seed 的实验；写出一个有证据的判断和一个局限。
- 保存与带走：确认结果对应哪个版本，导出研究包。
- 第二次访问：重新打开原项目，继续一次参数或机制修改，能找到第一次的版本与结果。

每个步骤只使用产品界面。观察者可以解释任务，不替用户补文件、改数据库或操作后台；
任何介入都记录，介入后的成功不算“独立完成”。

## 三人观察与优先级调整

使用 [acceptance.json](evidence/invited-queue/acceptance.json) 中 U1/U2/U3 的匿名位置。
实际身份单独保存在获准的私有记录中；不在仓库保存邮箱、登录信息或原始用户材料。
每项通过须引用时间、版本和证据；未尝试为 null，失败为 false，不能以没有报错推断成功。

退出条件：3 人均完成案例探索；至少 2 人无开发者修复地完成比较、解读证据，
并在第二次访问继续研究。当前三个位置全未观察，不产生成功率。
记录可信 usage 费用和未知预留两栏，不相加包装为最终账单。

登录阻断推动 #75；等待/恢复阻断推动 #37 对应子项；看不懂结果优先改研究引导。
未达标时先修实际阻断。公开扩张前另查项目隐私、内容许可、删除和导出规则。
