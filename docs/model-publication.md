# Reviewed user model publication

Issue #35 adds a pre-publication workflow to the existing immutable ModelCatalog.
It does not replace the existing catalog lifecycle. Ordinary users prepare and
submit from their Model workspace. Operators review frozen research, then approve
and publish, request changes, or reject. The candidate is never an editable link
into the user's current project.

## Readiness policy v1

The server requires a saved Revision, a valid persistent Spec and execution lock,
nonempty parameter and metric declarations, scope and limitations, and no active
model-editing Turn. At least one completed baseline/intervention group must use
the same source and Spec hashes as the selected model, include all declared seeds
and configurations, and contain a genuinely different intervention. Every child
must have a completed, valid, persisted result. Failed, partial, cancelled,
missing, rejected, or other-version results cannot make a group pass. Model-level
rejection disqualifies that model. A new chat-only checkpoint with identical files
and Spec does not invalidate otherwise eligible experimental evidence.

Passing this gate does **not** certify scientific correctness. Operators must
review the question, assumptions, mechanisms, parameter/metric interpretation,
comparison design, limitations, and reproducibility before approving.

The complete #32 research export is built and verified before submission. The UI
explicitly says that the administrator receives the current model **and complete
research history**, including old versions, failure/cancellation records, and
evidence. Export limits and sensitive-path rejection still apply. The official
copy package contains current public model/app/experiments/docs files with their
original bytes; only the platform README is regenerated by the existing copy
workflow. Other source roots fail explicitly. The original source TAR and exact
Spec remain in the frozen, access-controlled research ZIP.

## API and durability

- `GET /api/workspaces/:id/publication-readiness` performs read-only checks.
- `GET /api/workspaces/:id/model-submissions?before=:id` lists 20 candidates/page.
- `POST /api/workspaces/:id/model-submissions` requires `Idempotency-Key` and
  `{modelId, version, title, description, source:{revisionId,filesSha256,specSha256}}`.
- `GET /api/model-submissions/:id/export` downloads for the current project owner.
- `GET /api/admin/model-submissions?before=:id` lists the operator review queue.
- `GET /api/admin/model-submissions/:id/export` downloads frozen review research.
- `POST /api/admin/model-submissions/:id/review` requires `Idempotency-Key` and
  `{decision:'approve'|'request-changes'|'reject', note}`.

Owner membership, tenant status, current auth version, and server-side operator
roles are authoritative. No browser role claim authorizes publication. The
submission input must match the exact prepared source version. Reads and source
hashing do not start a simulation or contact an LLM.

Candidate content and research ZIPs are create-only, content-addressed R2 objects.
D1 stores immutable source identity, digests, readiness, and object receipts.
Public API views omit internal object keys. Complete research ZIPs are never
exposed through the public model catalog. Approval first records `publishing` and
a frozen catalog draft atomically, then resumes the existing upload → validate →
publish transitions. A response loss retries those identities. Another current
operator may resume with a separate audited intent. A publishing candidate cannot
be reversed to request changes or rejected. A requested change requires a newly
saved Revision and a new submission. New source edits never mutate submitted or
published content.

Apply `0009_model_submissions.sql` with the normal catalog migration process before
releasing these routes. This code change does not apply migrations remotely or
alter live runtime/model settings. Orphaned immutable uploads from an unsuccessful
submission are not automatically garbage-collected in this increment.

## Local validation and remaining live acceptance

The local protocol tests cover owner/operator ACL, immutable snapshot triggers,
submission and review response loss, stale source, request changes, rejection,
revoked roles, repeated publication, and isolated project copy identity. A real
local Workspace/Gateway/D1/RevisionStore/R2 test computes Python baseline and
intervention results, freezes and downloads the actual ZIP, replays it, edits the
source afterward, restarts the Workspace, approves the frozen candidate, and runs
the published Python bytes in an independent directory. This test seeds local
research records and identity fixtures; it is not ordinary-user cloud dogfooding.
Chrome tests verify full-history disclosure, responsive layout, and exact frozen
submission/approval retries after refresh without automatic mutation.

The first three official models (queue/service, inventory/replenishment, and
maintenance/resource allocation) remain a separate real ordinary-user acceptance
requirement. They must be created through the normal modeling and experiment
workflow, submitted through this UI, reviewed by an operator, and copied/run by a
fresh user. No repository special packages or direct catalog insertion may count
as those three models. No such cloud publication is claimed by this increment.
