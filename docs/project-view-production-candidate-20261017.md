## Candidate boundary

The browser runtime and its capacity are new, separate authorities. The intended additive resources are `PROJECT_VIEW_RUNTIME` / `ProjectViewRuntime` and `PROJECT_VIEW_CAPACITY` / `ProjectViewCapacity`; only the former associates with a dedicated browser image. The [review-only resource intent](../infra/project-view-production.patch.example.json) is a partial additive template, deliberately not a deployable Worker configuration. Publication must preserve the complete actual baseline arrays and original Workspace namespace.

The capacity singleton is `project-view-capacity-v1`, with at most one occupied session globally and therefore at most one per user. It stores the complete canonical session identity, deadline and cleanup tombstone in SQLite. The identity binds schema, session, operation, tenant/project/workspace/generation, user/authVersion, package digest, view and policy digest. Same-identity admission is idempotent; reused session/operation identities, changed deadlines and terminal reacquisition are rejected. Time expiry alone never returns a slot, and new users/projects/policies cannot bypass an occupied slot.

Capacity invokes only the derived original runtime actor's read-only `status({identity})`. Admission requires that runtime to recognize the original identity as starting/running. Release requires independently persisted `closed`, `cleanupConfirmed=true` and the exact original `cleanupProofId`; a caller-supplied boolean is insufficient. Runtime status must not queue behind the close operation that is waiting for capacity release. Cleanup received before a delayed acquire writes a terminal tombstone even if no slot was acquired, fencing that late request. Unknown execution retains capacity; no alarm or request automatically replays an original create/start operation.

The capacity Durable Object exposes private RPC acquire/release only, validates the fixed singleton identity, and requires the exact configured policy hash on new admission. Release still works after disabling/changing admission configuration if the original runtime proves cleanup. Persistent terminal records are not removed by expiry or restart.

## Cleanup and revocation boundary

The authenticated cleanup endpoint accepts only the original session ID and workspace ID from a currently authenticated active user. It resolves the original owner internally and can close that owner's session after project membership withdrawal, project archival, policy stop or generation change. It returns cleanup status; the original runtime identity never becomes a client credential. Unconfirmed cleanup keeps the original capacity occupied and prevents the panel from creating a replacement session.

Platform user revocation is different: the existing operator action sets the user to revoked and increments authVersion. An invalid/expired cookie or a revoked user cannot read, command or actively close sessions through that cookie. The persisted runtime alarm handles abandoned sessions after 10 seconds without a poll or the five-minute absolute deadline, then reconciles destruction and capacity release; unknown cleanup retains capacity and retries only the original cleanup. This candidate does not claim that a revoked user's old cookie can actively clean up a session, nor that a deadline alone proves release. Real identity/container revocation and release remain pending acceptance evidence.
