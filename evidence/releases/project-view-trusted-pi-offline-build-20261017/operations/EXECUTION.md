# One fixed-base route and pull — reviewable operations, not a grant

These independent operation files supplement the unchanged 30,515-byte `c92e672ca39d10d61467801f457147e3ee9cf2cfbbbe8b96d00a618a6a208bae` nine-file payload. They do not replace its build/probe contract, create a credential, or authorize execution. Current preparation/tests use fake data only.

A future direct human grant must name both archive and operations-manifest hashes and the reviewed packet commit. Root records it in a private0600 JSON file using schema `trusted-pi-offline-route-pull-grant/v1`, with `authority:direct-human-instruction-recorded-by-root`, `rootReviewCompleted:true`, nonempty `humanInstruction`, a new `requestId`, and UTC `startsAt`/`endsAt` at most15minutes apart. Required target fields are `accountId`, `registryHost`, `baseImage`, `recipient:AMD128`, `remoteDirectory`, `archiveSha256`, `archiveBytes`, `operationsManifestSha256`, `packetCommit`; exact values are in `scope.json`/the operator. `operations` equals the operator's five-operation list; `credential` is exactly `{"expiration_minutes":15,"permissions":["pull"]}`; `route` is exactly `{"remoteBind":"127.0.0.1:7897","localDestination":"127.0.0.1:7892"}`. All six exclusions (`allowRegistryPush`, `allowCloudAppUpdate`, `allowRealProviderTurnRun`, `allowNewSubscription`, `allowOAuthTransfer`, `allowAutomaticRefreshLoginOrNewScopes`) must be false. Missing grant/hash/source/target/commit/archive verification stops before OAuth, SSH or API. There is no automatic refresh, interactive login, new scope, account fallback or retry.

After the separately authorized bounded transfer/extraction of the exact nine-file payload to the fixed new AMD directory, run the reviewed local operator with a Python3.9+ interpreter:

```text
python3 operations/pull-operator.py --execute --grant <root-private-grant.json> --grant-sha256 <root-reviewed-raw-SHA> --operations-sha256 <raw-operations-manifest-SHA> --archive <original-c92e.tar.gz> --state-root <new-private-local-operation-record-directory>
```

This command is a template, not permission. The CLI has no injected-client or alternate target switch. Importing either Python file is inert. It checks every operation file against the manifest and the actual reviewed Git commit. It creates an exclusive UUID intent directory before contacting SSH/API and never deletes it. Existing UUIDs fail. Root must not create a new UUID/token/route to retry an unknown original operation.

The local operator starts one original owned SSH process with `-R 127.0.0.1:7897:127.0.0.1:7892`, fixed alias `AMD128`, no agent/X11/control-master forwarding and no inherited configured forwards. Only public frozen receiver code/identity is in remote argv. It invokes `/usr/bin/python3` on AMD. The receiver verifies the nine actual payload paths/hashes and original directory/socket/proxy, writes its original PID plus Linux start ticks, verifies from Linux/proc that the actual7897 listener binds only127.0.0.1 (rejecting wildcard/IPv6/other binds), and sends a safe ready message before any credential POST. This checks actual binding even when sshd GatewayPorts could override the requested address. Unsupported Python/daemon/schema/proxy/receiver output stops, without replacing an input or command.

Only then does the operator read **the existing local** `~/.wrangler/config/default.toml` in memory, requiring private ownership, a valid token with at least120seconds remaining, and the original exact five OAuth scopes. The OAuth token is used only locally via the existing fixed `http://127.0.0.1:7892` proxy to call once:

```text
POST https://api.cloudflare.com/client/v4/accounts/8b0d70250211aa10d89e20605a1c7e5e/containers/registries/registry.cloudflare.com/credentials
{"expiration_minutes":15,"permissions":["pull"]}
```

HTTP201/success is required. No redirect or automatic retry. Its required result fields `account_id`, `registry_host`, `username`, `password` are validated (username is not guessed) and go directly from local memory to the same SSH stdin envelope. Neither OAuth nor registry password appears in MCP/tool results, command arguments, environment, shell history, local files, stdout or debug logs. The token is account-registry scoped; exact-repository restriction is enforced by this fixed operator/receiver, not represented as a token permission. The temporary loopback reverse forward reaches a general existing proxy; it is not a per-repository HTTP firewall. OAuth never reaches AMD.

The receiver writes only a task-private0700 Docker directory with a0600 `config.json` containing base64 auth; base64 is secret, not encryption. It uses no `docker login` argv, credential helper or token environment. One fixed command uses `/usr/bin/docker --host unix:///var/run/docker.sock --config <original-task-config> pull --platform linux/amd64 <exact9b76-reference>`. Environment is PATH only. Pull wall limit600seconds, inspect30seconds, each stdout/stderr≤128KiB with any discarded bytes failing. Raw external output is not printed/saved; counts/SHA only. Exact digest/OS/architecture are checked with authoritative image inspect; local image Id is recorded separately and is not assumed to be a registry manifest or OCI config. No push, tag, build, container or Cloudflare application operation occurs in these files.

The receiver deletes and verifies absence of auth config in `finally`, records its terminal status, and exits. An original operation deadline/SIGTERM/SIGHUP/SIGINT stops its own child process group; daemon-side pull completion cannot be inferred from CLI termination, so interrupted/lost ACK outcomes remain unknown. The operator closes/terminates only its own original SSH process group and then performs a fresh independent SSH readback **without forwarding**. Acceptance requires original receiver PID/start-tick identity absent, task auth directory absent, an actual original terminal record, and remote7897 `ECONNREFUSED`(111), as well as the original successful pull terminal. Empty lists, unrelated PIDs or generic errors do not prove cleanup. No shared SSH session, arbitrary listener owner, daemon config, unrelated file/container/image is killed or removed. Local and remote intent/terminal/error history is retained.

If the ACK/cleanup is unknown, the sole further command is original-identity readback (same grant/source/archive hashes and UUID, `--readback-only` replacing `--execute`); it never creates a credential, relay or receiver. Cleanup readback after the grant expires is allowed, but it cannot promote a failed/unknown pull to success. If original receiver is still alive, wait for its fixed deadline and read that identity again; do not mint or replay. If its deadline/signal cannot be confirmed, stop for root reconciliation rather than invent success.
